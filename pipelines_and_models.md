## ЧАСТЬ 1: ПАЙПЛАЙНЫ

### Обозначения

```
[Агент]          — обычный шаг пайплайна
[Агент] ─(файл)─ — агент читает/пишет файл
[⟳ rework ×3]    — цикл реработки, максимум 3 итерации
──►               — направление потока
═══►              — переход на следующий этап
```

---

### 1. BUGFIX SIMPLE

**Когда используется:** Простые баги, не требующие глубокого планирования.

```
┌──────────────┐     ┌──────────┐     ┌─────────┐
│ bugfix-triage │ ──► │  worker  │ ──► │ utility │
└──────────────┘     └──────────┘     └─────────┘
```

| Агент | Что делает |
|-------|-----------|
| `bugfix-triage` | Первичный анализ бага: определяет критичность, область, воспроизводимость |
| `worker` | Реализует исправление — простые задачи, не требующие глубокого анализа |
| `utility` | Финальная валидация: синтаксис, форматирование, проверка стиля кода |

---

### 2. BUGFIX DEEP

**Когда используется:** Сложные баги, требующие планирования, ревью и циклов реработки.

```
┌───────────────┐     ┌──────────┐     ┌───────────────────┐     ┌──────────┐     ┌──────────────┐
│ bugfix-triage │ ──► │ plan-bug │ ──► │   execute-bug     │ ──► │  advisor │ ──► │ dev-reviewer │
└───────────────┘     └──────────┘     └───────────────────┘     └──────────┘     └──────────────┘
                      пишет                   читает                                     │
                      bug_plan.md           bug_plan.md                                  ▼
                                                                                    ┌──────────┐
                                                                                    │ rework   │
                                                                                    └──────────┘
                                                                                         │
                                                                                         ▼
                                                                               ┌─────────────────────┐
                                                                               │ consistency-checker │
                                                                               └─────────────────────┘
                                                                                         │
                                                                            ┌──── ── ── ─┴─ ── ── ────┐
                                                                            │  [⟳ rework loop, max 3] │
                                                                            └──── ── ── ─┬─ ── ── ────┘
                                                                                         │
                                                                                         ▼
                                                                                    ┌─────────┐
                                                                                    │ utility │
                                                                                    └─────────┘
```

| Агент | Что делает |
|-------|-----------|
| `bugfix-triage` | Первичный анализ бага: воспроизведение, определение корневой причины |
| `plan-bug` | Составляет план исправления, записывает в `bug_plan.md` |
| `execute-bug` | Реализует исправление по плану из `bug_plan.md` |
| `advisor` | Step-boundary advisory-ревью (read-only): заметки nit/concern/blocker перед ревью |
| `dev-reviewer` | Ревью кода: проверяет качество, безопасность и корректность решения |
| `rework` | Исправляет замечания, выявленные на ревью |
| `consistency-checker` | Проверяет соответствие архитектуре проекта (читает `ARCHITECTURE.md`) |
| `utility` | Финальная валидация: синтаксис, форматирование |

> **⟳ Цикл реработки:** Если `consistency-checker` или `dev-reviewer` находят проблемы,
> управление возвращается к `rework` (до 3 итераций).

### 4. DEV SIMPLE (с планом)

**Когда используется:** Задачи средней сложности, когда план уже существует (`plan_exists=true`).

```
┌──────────┐     ┌─────────────────────┐     ┌─────────┐
│  worker  │ ──► │ consistency-checker │ ──► │ utility │
└──────────┘     └─────────────────────┘     └─────────┘
                         │
            ┌──── ── ── ─┴─ ── ── ────┐
            │  [⟳ rework loop, max 3] │
            └──── ── ── ─┬─ ── ── ────┘
                         │
                   (возврат к worker)
```

| Агент | Что делает |
|-------|-----------|
| `worker` | Реализует задачу в соответствии с планом |
| `consistency-checker` | Проверяет соответствие реализации плану и архитектуре |
| `utility` | Финальная валидация: синтаксис, форматирование |

> **⟳ Цикл реработки:** Если `consistency-checker` находит расхождения с планом,
> управление возвращается к `worker` (до 3 итераций).

### 5. DEV COMPLEX

**Когда используется:** Сложные задачи разработки, требующие планирования, наставничества и ревью.

```
┌──────────────┐     ┌───────────────┐     ┌──────────┐     ┌──────────────┐     ┌──────────┐
│ dev-planner  │ ──► │ dev-professor │ ──► │  advisor │ ──► │ dev-reviewer │ ──► │  rework  │
└──────────────┘     └───────────────┘     └──────────┘     └──────────────┘     └──────────┘
   пишет                читает                                                        │
 dev_plan.md          dev_plan.md                                                     ▼
                                                                            ┌─────────────────────┐
                                                                            │ consistency-checker │
                                                                            └─────────────────────┘
                                                                                      │
                                                                         ┌──── ── ── ─┴─ ── ── ────┐
                                                                         │  [⟳ rework loop, max 3] │
                                                                         └──── ── ── ─┬─ ── ── ────┘
                                                                                      │
                                                                                      ▼
                                                                                 ┌─────────┐
                                                                                 │ utility │
                                                                                 └─────────┘
```

| Агент | Что делает |
|-------|-----------|
| `dev-planner` | Планирует архитектуру и подход к решению, **записывает план в `dev_plan.md`** |
| `dev-professor` | Реализует сложный код, следуя плану и лучшим практикам |
| `advisor` | Step-boundary advisory-ревью (read-only): заметки nit/concern/blocker перед ревью |
| `dev-reviewer` | Проводит ревью: качество, паттерны, потенциальные проблемы |
| `rework` | Исправляет замечания по ревью |
| `consistency-checker` | Валидирует соответствие архитектуре проекта |
| `utility` | Финальная валидация: синтаксис, форматирование |

> **⟳ Цикл реработки:** Если `consistency-checker` или `dev-reviewer` находят проблемы,
> управление возвращается к `rework` (до 3 итераций).

### 6. DEV SUPERCOMPLEX

**Когда используется:** Очень сложные задачи с планом >3 шагов или огромным объёмом работ.
Полный цикл ревью/валидации выполняется **для каждого шага** плана.

```
┌─────────────────────────────────────────────────────────────────┐
│  Для КАЖДОГО шага плана:                                        │
│                                                                 │
│  ┌──────────────┐   ┌───────────────┐   ┌──────────────┐       │
│  │ dev-planner  │──►│ dev-professor │──►│ dev-reviewer │       │
│  └──────────────┘   └───────────────┘   └──────────────┘       │
│    пишет               читает                                  │
│  dev_plan.md         dev_plan.md                               │
│                                              │                  │
│                                              ▼                  │
│                                 ┌─────────────────────┐         │
│                                 │ consistency-checker │         │
│                                 └─────────────────────┘         │
│                                              │                  │
│                                 ┌──── ── ── ─┴─ ── ── ────┐   │
│                                 │  [⟳ rework loop, max 3] │   │
│                                 └──── ── ── ─┬─ ── ── ────┘   │
│                                              │                  │
│                                              ▼                  │
│                                        ┌─────────┐             │
│                                        │ utility │             │
│                                        └─────────┘             │
└─────────────────────────────────────────────────────────────────┘
```

| Агент | Что делает |
|-------|-----------|
| `dev-planner` | Планирует конкретный шаг реализации, **записывает план в `dev_plan.md`** |
| `dev-professor` | Реализует код для текущего шага |
| `dev-reviewer` | Ревью кода текущего шага |
| `consistency-checker` | Проверяет архитектурное соответствие текущего шага |
| `utility` | Валидация синтаксиса после каждого шага |

> **⟳ Цикл реработки:** Для каждого шага — до 3 итераций реработки.
> Триггер: план с >3 шагами ИЛИ явный запрос пользователя ИЛИ огромный объём работ.

### 10. Auto-DOCS Hook

**Когда используется:** Автоматически после завершения пайплайнов BUGFIX или DEV.

```
┌─────────────────────────────────────────┐
│  Завершён пайплайн BUGFIX / DEV        │
│  (последний шаг — utility)              │
└──────────────────┬──────────────────────┘
                   │
                   ▼
        ┌─────────────────────────┐
        │ requires_docs_update    │
        │        == true ?        │
        └────────┬───────┬────────┘
                 │       │
            Да   │       │  Нет
                 ▼       ▼
    ┌──────────────┐   ┌──────┐
    │ docs-writer  │   │ Конец│
    └──────┬───────┘   └──────┘
           │
           ▼
    ┌─────────┐
    │ utility │
    └─────────┘
```

**Условия срабатывания** (`requires_docs_update: true`):

- Был изменён `bug_plan.md` или `dev_plan.md`
- Были изменены любые `*.md` файлы (README, ARCHITECTURE, docs/)
- Изменилось публичное API
- Добавлены значимые docstrings

**Пайплайны с хуком:** BUGFIX SIMPLE, BUGFIX DEEP, DEV SIMPLE, DEV COMPLEX, DEV SUPERCOMPLEX.
**Пайплайны без хука:** DEVOPS, DOCS (рекурсивно), PLAN, RESEARCH.

## ЧАСТЬ 2: МОДЕЛИ И ИХ НАЗНАЧЕНИЕ

### Общая архитектура

Система использует **двойную архитектуру первичных агентов**:
- **orchestrator** — операционные и исполнительные задачи (BUGFIX, DEVOPS, DEV, DOCS)
- **plankestrator** — плановые и исследовательские задачи (PLAN, RESEARCH)

Оба первичных агента работают на одной модели, но имеют разные routing tables и не вызывают друг друга.

---

### Первичные агенты

| Агент | Модель | Роль |
|-------|--------|------|
| `orchestrator` | bifrost-litellm/QWEN3.7-plus | Управление операционными задачами: BUGFIX, DEVOPS, DEV, DOCS. Маршрутизация задач по агентам. |
| `plankestrator` | bifrost-litellm/QWEN3.7-plus | Управление плановыми задачами: PLAN, RESEARCH. Координация исследований и планирования. |

**Почему Qwen 3.7 Plus:** Баланс производительности и качества для маршрутизации и координации. Модель хорошо справляется с пониманием контекста и принятием решений о том, какой агент должен обработать задачу.
